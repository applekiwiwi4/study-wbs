## AI Agent — 3-3 GraphRAG 이론 (연결된 정보를 찾는 지식그래프)
**배운 개념 (내 말로)**
- **RAG는 "비슷한 문장"을 찾고, 그래프는 "연결된 관계"를 따라간다.**
  - 예: "E3 오류의 원인 부품은? 그 부품을 다른 제품도 쓰나?"
  - 매뉴얼에는 "팬 모터 이상"만 있다. 부품 번호(FM-20)와 그 부품을 쓰는 제품은 부품 관리 데이터(BOM)에 흩어져 있어서 어느 한 조각에도 답이 없다.
- **RAG가 약한 질문 4가지**
  - 여러 단계 연결: 오류 → 원인 부품 → 그 부품을 쓰는 제품
  - 집계: 오류를 가장 많이 일으키는 부품 (상위 몇 개 조각으로는 전체를 셀 수 없다)
  - 영향 범위: 공급사 문제로 영향받는 제품 (관계를 거꾸로 따라가야 한다)
  - 조직·담당: 이 오류는 어느 부서 담당인가
- **지식그래프 구성 요소**
  - 노드(대상): AirPure 300, FM-20, E3, AS센터
  - 레이블(노드 종류): Product, Part, Error, Dept
  - 관계(방향과 이름이 있는 선): HAS_PART, HAS_ERROR, CAUSED_BY, HANDLED_BY
  - 속성(붙는 정보): name, warranty_years
  - 품질팀 질문이 "선 따라가기"가 된다: AirPure 300 → E3 → FM-20 → (거꾸로 HAS_PART) → DryMax 16L
- **표와 그래프는 같이 쓴다.** 매출 합계처럼 정형 데이터는 표(관계형 DB)가 잘하고, 연결이 깊은 질문은 그래프가 잘한다. 표에서는 JOIN이 3~4번 필요한 질문이 그래프에서는 선 3개 따라가기다.
- **그래프는 "무엇을 물어볼지"에서 거꾸로 설계한다.** 질문마다 필요한 노드와 관계를 먼저 적고 만든다.
- **이미 정리된 표가 있으면 표에서 바로 그래프를 만든다.** LLM으로 문서에서 뽑으면 "팬모터", "FM20", "팬 모터 FM-20"처럼 이름이 제각각이 되기 쉽다.
- **Cypher 기초** (그림 그리듯 쓰는 질의 언어. `( )`는 노드, `-[ ]->`는 관계)
  - `MERGE`: 없으면 만들고 있으면 그대로 쓴다. 적재 코드를 여러 번 돌려도 중복이 안 생긴다. `CREATE`는 실행할 때마다 새로 만든다.
  - `MATCH ... WHERE ... RETURN`: 찾기. SQL의 `SELECT ... FROM ... WHERE`에 해당한다.
  - `count`, `collect`: 세기와 모으기. `GROUP BY` 없이 자동으로 묶인다.
- **그래프에서 답 찾는 방법 3가지**
  - 템플릿 질의: 미리 만든 Cypher에 값만 넣는다. 정확하고 안전해서 CS 에이전트 같은 업무 질문에 맞다.
  - Text2Cypher: LLM이 Cypher를 쓴다. 처음 보는 질문도 되지만 틀리거나 위험한 쿼리(전부 삭제)가 나올 수 있다.
  - 하이브리드: 문서 검색(어떻게 조치하나)과 그래프(어떤 부품·보증·담당 부서)를 함께 근거로 쓴다. 고장 문의 답변에 맞다.
- **Text2Cypher 안전장치**: 읽기 전용 계정, 실습 DB에서만 사용, 자주 쓰는 질문은 템플릿 질의로 바꾸기
- 도구: 그래프 DB는 Neo4j(AuraDB Free), 파이썬 연습은 NetworkX로 메모리에 같은 그래프를 만든다(3-4 실습).
- 참고로 Microsoft GraphRAG는 대량 문서에서 그래프를 자동으로 만들고 주제별로 미리 요약한다. 전체 요약 질문에 강하지만, 준비할 때 LLM 호출이 매우 많아 무료 한도로는 부담이 크다.

**확인 문제 풀이 (내 답)**
- RoboClean X가 쓰는 부품 id 목록:
  ```cypher
  MATCH (:Product {name: "RoboClean X"})-[:HAS_PART]->(p:Part) RETURN p.id
  ```
- `MATCH (e:Error)-[:HANDLED_BY]->(d:Dept {name: "AS센터"}) RETURN count(e)`는 AS센터가 담당하는 오류코드 개수다.

## ROS — 자율주행 과정 3일차 ② 실습 (움직이고, 멈추고, 보고하는 로봇)
**배운 개념 (내 말로)**
- **`amr_basics` 패키지**: `ros2 pkg create --build-type ament_python`으로 만들었다. 의존 패키지(rclpy, geometry_msgs, sensor_msgs, std_srvs, nav_msgs, tf2_ros)는 `package.xml`에 적히고, 실행할 노드는 `setup.py`에 등록한다.
- **`scan_frame.py` (LiDAR 방향 보정)**: TurtleBot4의 LiDAR는 90도 돌아간 채 달려 있다. 라이다 기준 0도는 실제로 로봇의 왼쪽이다. TF에서 `base_link`와 라이다 사이 회전각을 읽어 로봇 정면 기준으로 바꾼다. TF를 못 받으면 파라미터 기본값 90도를 쓴다.
- **`safety_stop.py` (안전 노드, `/cmd_vel`의 유일한 발행자)**
  - `/cmd_vel_raw`와 `/scan`을 받아 전방 최근접 거리 d로 판단한다.
    - d > 0.7m: 그대로 통과 (NORMAL)
    - 0.4m < d ≤ 0.7m: 비례 감속 (SLOW). `ratio = (d - 0.4) / (0.7 - 0.4)`를 곱한다.
    - d ≤ 0.4m: 전진 금지 (STOP). 회전과 후진은 허용해서 돌아 나갈 수 있다.
  - `/scan`은 `qos_profile_sensor_data`로 구독한다.
  - 명령이 0.5초 이상 끊기면 정지 명령을 한 번 보낸다. 순찰 노드가 죽은 경우를 대비한 것이다.
  - Gazebo 바퀴는 마지막 속도 명령을 계속 유지하므로, 안전 노드가 꺼질 때 반드시 정지 명령을 보내게 했다.
- **`patrol_node.py` (순찰)**: "직진 6초 → 좌회전 90도"를 반복한다. `/cmd_vel_raw`로만 발행한다.
- **`status_server.py` (상태 보고)**: `/robot_status` 서비스(Trigger)로 위치, 배터리, 임무, 안전 상태를 한 줄로 답한다. `/mission_state`는 1초마다 발행한다.
- **파라미터는 실행 중에 바꿀 수 있다.** 안전 노드가 콜백마다 값을 다시 읽어서 `ros2 param set`이 바로 반영된다.
- 시뮬레이터와 함께 쓰는 노드에는 항상 `use_sim_time:=true`를 넣는다.

**실행한 것**
```bash
ros2 pkg create --build-type ament_python --license Apache-2.0 amr_basics \
  --dependencies rclpy std_msgs geometry_msgs sensor_msgs std_srvs nav_msgs tf2_ros
lift_build                                                        # 빌드 + 환경 다시 읽기
ros2 launch nav2_minimal_tb4_sim simulation.launch.py             # T1
ros2 run amr_basics safety_stop --ros-args -p use_sim_time:=true  # T2
ros2 run amr_basics status_server --ros-args -p use_sim_time:=true # T3
ros2 run amr_basics patrol_node --ros-args -p use_sim_time:=true  # T4
ros2 topic echo /safety_state
ros2 service call /robot_status std_srvs/srv/Trigger "{}"
ros2 param set /safety_stop stop_dist 0.6
rqt_graph
ros2 topic echo /scan --qos-reliability reliable --once
ros2 topic echo /scan --qos-reliability best_effort --once
```

**결과**
- 로봇이 사각형으로 순찰했다. Gazebo에서 로봇 앞에 상자를 놓자 `/safety_state`가 NORMAL → SLOW → STOP으로 바뀌었다. 멈춘 뒤에는 회전해서 다음 변으로 돌아 나갔다.
- `/robot_status`를 호출하면 위치, 배터리, 임무(IDLE), 안전 상태가 한 줄로 왔다.
- `stop_dist`를 0.6으로 바꾸자 상자 앞에서 더 일찍 멈췄다.
- **최종단 배선 시험**: 순찰 노드가 명령을 계속 보내는 중에 안전 노드만 껐다. 로봇이 바로 멈추고 다시 움직이지 않았다. 안전 노드를 다시 켜자 순찰이 이어졌다.
- `rqt_graph`에서 `/patrol_node → /cmd_vel_raw → /safety_stop → /cmd_vel` 화살표를 확인했다. `/patrol_node`에서 `/cmd_vel`로 바로 가는 화살표는 없었다.
- QoS 실험

| 구독 QoS | 발행 QoS (`/scan`) | 수신 |
|---|---|---|
| RELIABLE | BEST_EFFORT | 안 옴 (오류도 없음) |
| BEST_EFFORT | BEST_EFFORT | 바로 1개 받음 |

- 과제 계산: 원하는 속도 0.15m/s, 전방 0.55m이면 `ratio = (0.55 - 0.4) / 0.3 = 0.5`라서 실제 속도는 0.075m/s다.
- `~/project_lift`에 `3일차: amr_basics (safety_stop / patrol_node / status_server)`로 커밋했다.

## 문제와 해결
| 문제 | 원인 | 해결 |
|---|---|---|
| 라이다 기준 "정면"이 실제로는 로봇 왼쪽임 | TurtleBot4 LiDAR가 90도 돌아간 채 장착되어 있다. | `scan_frame.py`에서 TF로 장착 각도를 읽어 더했다. TF가 없을 때를 대비해 파라미터 기본값(90도)도 두었다. |
| 안전 노드를 꺼도 로봇이 마지막 속도로 계속 달릴 수 있음 | Gazebo 바퀴 플러그인은 마지막 명령을 계속 유지한다. | 안전 노드가 종료될 때(Ctrl+C) 정지 명령을 보내게 했다. 명령이 0.5초 끊겨도 정지 명령을 보낸다. |
| 안전 노드를 껐는데 로봇이 움직이면 배선이 잘못된 것 | 순찰 노드가 `/cmd_vel`로 직접 발행하면 안전 노드를 건너뛴다. | 순찰 노드의 발행 토픽이 `/cmd_vel_raw`인지 확인하고, `rqt_graph`로 직렬 배선을 그림으로 확인했다. |
| RAG로는 "그 부품을 쓰는 다른 제품" 질문에 답이 없음 | 부품과 제품의 연결 정보가 문서 한 조각에 들어 있지 않다. | 제품·부품·오류·부서를 지식그래프로 만들고 관계를 따라가는 방식으로 이해했다. 3-4에서 NetworkX로 직접 만든다. |
