## AI Agent — 3-1 LangGraph ② 이론 (AI 판단, 도구, 기억, 사람 승인)
**배운 개념 (내 말로)**
- **판단은 LLM이 하고, 갈림길은 코드가 정한다.**
  - `classify` 노드에서 LLM이 문의를 분류해 `ticket` 칸에 적는다.
  - 조건 엣지 함수는 그 칸을 보고 `order`로 갈지 `retrieve`로 갈지 고른다.
  - LLM이 "다음 노드로 가"라고 직접 정하게 하는 것보다 예측하기 쉽고 테스트하기 쉽다.
- **LLM이 꼭 필요한 노드에만 쓴다.**
  - LLM이 필요한 노드: 문의 분류, 답변 작성
  - 코드로 충분한 노드: 주문 조회(DB 조회), 문서 검색(임베딩 검색), 위험 문의 확인(긴급도 칸 보기)
  - 그래서 CS 에이전트는 문의 한 건에 LLM을 2번만 부른다. LLM 호출은 시간과 비용과 무료 한도를 쓴다.
- **ReAct와 `create_agent`**
  - ReAct는 생각 → 도구 실행 → 결과 확인 → 다시 생각을 반복한다. `create_agent(model, tools, system_prompt)` 한 줄로 만든다.
  - 빠르고 유연하지만, 도구를 몇 번 부를지 모르고 같은 질문에도 경로가 바뀐다.
  - 상담이나 결재처럼 절차가 정해진 회사 업무는 직접 설계한 그래프가 더 안전하다.
- **기억: 체크포인터와 `thread_id`**
  - `compile(checkpointer=InMemorySaver())`를 쓰면 노드가 끝날 때마다 상태가 자동 저장된다. 게임의 자동 저장과 같다.
  - `thread_id`는 대화방 번호다. 같은 방이면 "그거 어디쯤 왔어요?"의 '그거'를 앞 대화에서 찾는다.
  - 대화가 길어지면 느려지고 비싸지므로 최근 6개 메시지(`messages[-6:]`)만 넘긴다.
  - 저장소는 실습용 `InMemorySaver`, 파일에 저장하는 `SqliteSaver`, 실제 서비스용 `PostgresSaver`가 있다.
- **사람 승인: `interrupt`**
  - 연기, 감전, 소송 언급, 환불 지급처럼 위험한 일은 `interrupt()`로 그 자리에서 멈추고 상담원 결정을 기다린다.
  - 결정이 나면 `Command(resume={"action": "approve"})`로 같은 대화방에서 이어서 실행한다.
  - 멈춘 상태는 체크포인터가 들고 있으므로, interrupt에는 체크포인터가 반드시 필요하다.
- **자주 쓰는 설계 패턴 4가지**
  - 라우터: 분류 후 종류별로 처리한다.
  - 도구 반복(ReAct): LLM이 도구를 골라 반복해서 쓴다.
  - 자기 점검: 근거가 부실하면 한 번 다시 검색한다.
  - 멀티 에이전트: 역할별 에이전트가 나눠서 일한다.
  - 처음에는 라우터와 필요한 곳에만 LLM을 쓰는 것으로 충분하다.

**CS 에이전트 설계도 읽기**
| 노드 | 종류 | 읽는 칸 | 쓰는 칸 | 실패하면 |
|---|---|---|---|---|
| classify | LLM | messages | ticket | 재시도 3회, 주문번호는 코드로 한 번 더 찾기 |
| order | 코드 | ticket.order_id | order_info | "주문을 찾을 수 없습니다" 전달 |
| retrieve | 코드 | ticket, messages | context, sources | 근거가 없으면 "확인 후 안내" |
| draft | LLM | ticket, order_info, context, messages | answer | 재시도 |
| review | 코드 + 사람 | ticket, answer | answer, messages | 위험 문의는 상담원 승인 대기 |

- 2-1 분류기(구조화 출력), 2-3 RAG 검색, 1-6 답변 초안이 이 그래프의 노드로 그대로 들어간다. 지금까지 만든 부품을 조립하는 단계다.

## ROS — 자율주행 과정 2일차 ② 실습 (프로젝트 환경과 센서 관찰)
**배운 개념 (내 말로)**
- **설치는 한 번에, 만드는 것은 하루씩.**
  - `setup_project.sh`로 다음을 한꺼번에 설치했다: Gazebo Harmonic(`ros-gz`), Nav2, SLAM Toolbox, TurtleBot3·4 시뮬레이션, MQTT(mosquitto)
  - 현장에서도 로봇 PC를 세팅할 때 명령을 하나씩 치지 않고 스크립트나 Docker로 같은 환경을 만든다.
- **공통 환경 파일 `lift.sh`**
  - 터미널마다 환경이 다르면 같은 명령이 창마다 다르게 동작한다. 그래서 ROS source, 프로젝트 경로, `ROS_DOMAIN_ID=30`, `LOCALHOST` 통신 범위, Gazebo 모델 경로, 줄임말(`lift_build`)을 한 파일에 모았다.
  - `~/.bashrc`에서 자동으로 실행되게 했다.
- **센서 토픽은 `BEST_EFFORT`로 발행된다.** 터미널에서 볼 때 `--qos-reliability best_effort`를 붙여야 값이 보인다. 이유는 3일차 QoS에서 배운다.
- **IMU `linear_acceleration.z`는 가만히 있어도 약 9.8이다.** 정지해 있어도 중력이 측정되기 때문이다.
- **센서가 원래 못 보는 것이 있다.**
  - LiDAR 높이에 걸리지 않는 선반이나 낮은 물체는 LiDAR 점에는 없고 깊이 영상에만 보인다.
  - "로봇이 장애물을 못 봤다"는 문제의 상당수는 센서가 볼 수 없는 위치나 재질이었던 경우다.
- **현장 정의서(M0)**: 지점 좌표(S1~S4, 충전, 엘리베이터, D1), 임무(MSN-1~3), 제약을 표로 채웠다. 제약은 통로 1.0m, 로봇 폭 0.34m, 2대 운용, 사람 통행이다. 성공 기준은 숫자와 측정 방법으로 적었다.

**실행한 것**
```bash
bash ~/project_lift/scripts/setup_project.sh          # 시뮬레이터·Nav2·도구 설치
cp ~/project_lift/scripts/lift.sh ~/lift.sh && echo "source ~/lift.sh" >> ~/.bashrc
bash ~/project_lift/scripts/check_env.sh               # 환경 점검
ros2 launch nav2_minimal_tb4_sim simulation.launch.py  # T1: Gazebo + RViz (TurtleBot4 창고)
ros2 run teleop_twist_keyboard teleop_twist_keyboard   # T2: 키보드 조종
ros2 topic hz /scan
ros2 topic echo /scan --once --qos-reliability best_effort | head -20
ros2 topic echo /imu --once
ros2 topic echo /odom --once --field pose.pose
ros2 topic echo /rgbd_camera/camera_info --once
```

**결과**
- 새 터미널을 열면 `[LIFT] 준비 완료 ROS=jazzy domain=30`이 뜬다.
- `check_env.sh`에서 ROS 2, Gazebo, 도구는 모두 `[ OK ]`가 나왔다. `amr_basics`, YOLO 가상환경, Ollama는 뒤 일차에 만들므로 `[WARN]`이 정상이다.
- 키보드(i, j, l, k)로 Gazebo 속 TurtleBot4가 움직였다.
- `/scan`이 계속 들어왔다.
- RViz에 LaserScan, 카메라 영상, 깊이 영상, TF를 추가해서 확인했다.
- `~/project_lift`에 git 저장소를 만들었다. `.gitignore`에는 build, install, log, 영상(mp4), 모델(pt), 측정 CSV를 넣었다.

## 문제와 해결
| 문제 | 원인 | 해결 |
|---|---|---|
| 예전 워크스페이스와 패키지가 섞일 수 있음 | `~/.bashrc`에 실전편 실습 때 쓰던 다른 워크스페이스 설정 줄이 남아 있으면, 같은 이름의 패키지가 섞이거나 Gazebo 기동이 실패할 수 있다. | `grep -n "setup.bash" ~/.bashrc`로 확인하고, `source ~/lift.sh`를 뺀 다른 워크스페이스 줄은 `#`로 막았다. 1일차의 `source /opt/ros/jazzy/setup.bash` 줄도 `lift.sh`가 대신하므로 지웠다. |
| `ros2 topic echo /scan`에 아무것도 안 나올 수 있음 | 센서 토픽은 `BEST_EFFORT`로 발행되는데, echo는 기본으로 `RELIABLE`을 요청해서 QoS가 맞지 않는다. | `--qos-reliability best_effort`를 붙여서 받았다. |
| LLM이 그래프 경로까지 정하면 동작을 예측하기 어려움 | ReAct는 같은 질문에도 도구 호출 순서와 횟수가 바뀔 수 있다. | 절차가 정해진 상담 업무는 직접 설계한 그래프로 하기로 했다. LLM은 분류와 작성 두 곳에서만 쓰고, 갈림길은 코드로 정한다. |
