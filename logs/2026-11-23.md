## AI Agent — 4-2 n8n 업무 자동화 이론
**배운 개념 (내 말로)**
- **업무 자동화 = "이런 일이 생기면(트리거) → 정해진 일들을 순서대로(노드)".**
  - 지금 사람이 하는 일: 문의 게시판을 수시로 확인하고, 읽어서 담당자에게 전달하고, 저녁마다 엑셀로 집계한다.
  - 자동화하면: 문의가 올라오면 바로 실행되고, AI가 분류해 담당 채널로 보내고, 매일 18시에 자동 집계해 메일로 보낸다.
- **n8n을 쓰는 이유**: 직접 설치(Community Edition)하면 무료이고 실행 횟수 제한이 없다. 데이터를 회사 서버에 둘 수 있어서 보안을 중시하는 회사가 많이 쓴다. Zapier는 쉽지만 무료 범위가 작고, Make는 실행 횟수가 제한된다.
- **기본 구조**
  - 워크플로: 자동화 하나 (노드를 연결한 그림)
  - 트리거 노드: Schedule(정해진 시간), Webhook(주소 호출), Form, Chat
  - 노드: HTTP Request(어떤 API든 부르는 만능 노드), IF·Switch(분기), Edit Fields(값 정리), Code, Wait, Discord·Slack·Gmail·Sheets(알림과 기록)
  - 실행 기록: 노드마다 입력과 출력이 남아서 디버깅에 쓴다.
  - Credentials: API 키와 계정을 노드에 직접 쓰지 않고 따로 저장한다.
- **데이터는 아이템 목록으로 흐른다.** 각 아이템이 `json`을 가진다. 대부분의 노드는 아이템마다 한 번씩 실행되므로 반복문을 따로 만들지 않는다. 문의가 2건이면 HTTP Request도 2번 호출된다.
- **표현식 `{{ }}`**: 앞 노드의 값을 꺼내 쓴다. 예: `{{ $json.ticket.urgency }}`, `{{ $('문의 접수 (Webhook)').item.json.body.id }}`, `{{ $now.toFormat('yyyy-MM-dd') }}`. INPUT 값을 끌어다 놓으면 자동으로 만들어진다.
- **LangGraph와 n8n은 생김새가 비슷하지만 잘하는 일이 다르다.** LangGraph는 AI 판단 흐름, n8n은 회사 시스템 사이의 연결 흐름에 강하다.
- **이 과정의 방식: 우리 AI를 API로 열고 n8n이 부른다.**
  - 판단(분류, 검색, 답변)은 파이썬 LangGraph가 맡는다. 흐름이 복잡하고, 테스트와 버전 관리가 필요하다.
  - 연결(언제 시작하고 어디로 보낼지)은 n8n이 맡는다. 메신저, 메일, 시트 연결이 클릭 몇 번이다.
  - FastAPI로 `POST /chat`에 `handle()`을 붙이면, n8n뿐 아니라 Dify, 웹 화면, 다른 시스템도 같은 AI를 재사용할 수 있다.
- **Docker 안의 n8n에서 `localhost`는 컨테이너 자신이다.** 내 PC의 API를 부르려면 `http://host.docker.internal:8000`을 쓴다.
- **운영할 때 챙길 것**
  - 가끔 실패하는 API: Retry On Fail (2회, 5초 간격)
  - 한 건 실패로 전체가 멈추지 않게: On Error → Continue
  - 실패 알림: Error Trigger 워크플로
  - 무료 LLM 분당 한도: Loop Over Items(1건씩) + Wait(5초). 2주차에 Groq 429를 한 건씩 보내서 해결한 것과 같은 방법이다.
  - 웹후크 주소는 누구나 부를 수 있으니 Header Auth를 건다. 워크플로 JSON을 GitHub에 올릴 때는 주소와 키가 없는지 확인한다.
- n8n 3.0(2026년 10월)부터 npm 설치 지원이 끝나서 Docker 설치가 표준이다.

**확인 문제 (내 답)**
1. 자동화할 일: 매일 저녁 9시(트리거) → 오늘 WBS 일지 파일 읽기 → AI로 한 줄 요약(처리) → 내 메신저로 보내기(결과)
2. Code 노드가 아이템 5개를 내보내면 다음 HTTP Request는 5번 실행된다.
3. `{{ $json.ticket.urgency }}`
4. 컨테이너 안의 `localhost`는 컨테이너 자신이라서 내 PC의 8000번 포트에 닿지 않는다.
5. 같은 로직을 n8n, Dify, 웹 화면이 재사용할 수 있고, 파이썬에서 테스트와 버전 관리를 할 수 있기 때문이다.

## ROS — 자율주행 과정 5일차 ① 이론·실습 준비 (센서 데이터 처리와 시각화)
**배운 개념 (내 말로)**
- **센서 처리 파이프라인: 받기 → 걸러내기 → 좌표 맞추기 → 판단값 만들기 → 발행**
  - 수백 개의 거리값이나 수십만 개의 픽셀을 상위 노드에 그대로 넘기지 않는다. "전방 0.85m", "기울기 경보"처럼 바로 판단에 쓸 수 있는 값으로 바꿔서 넘긴다.
- **LiDAR 처리**
  - `ranges[i]`의 각도는 `angle_min + i × angle_increment`다.
  - 측정 실패값(`inf`, `nan`)과 `range_min`보다 작은 값은 반드시 걸러낸다.
  - TurtleBot4는 LiDAR가 90도 돌아가 있어서 3일차 `scan_frame.py`로 로봇 기준 각도로 바꾼다.
  - LiDAR는 초당 수천 개의 값을 보내므로 파이썬 반복문 대신 numpy로 배열 전체를 한 번에 계산한다.
- **산업용 안전 필드** (ISO 3691-4, IEC 61496)
  - 경고 필드(Warning): 감속, 경고등. 이 과정에서는 전방 0.7m(`slow_dist`) 이내 비례 감속이다.
  - 보호 필드(Protective): 즉시 정지. 이 과정에서는 전방 0.4m(`stop_dist`) 이내 전진 0이다.
  - 필드 전환: 속도가 빠를수록 필드를 넓힌다 (과제 1).
  - 3일차 `safety_stop`이 이 두 필드를 구현한 노드였다. 다만 이것은 SW 보조 안전 기능이다. 실제 현장의 기능 안전은 인증된 하드웨어 안전 회로가 맡고, SW는 그 앞에서 부드러운 감속을 맡는다.
- **IMU 처리**
  - orientation(roll, pitch, yaw): 경사로와 전도 감시. yaw는 서서히 틀어진다.
  - `angular_velocity.z`: 회전 속도. 적분하면 오차가 계속 쌓인다(드리프트).
  - `linear_acceleration`: 충돌과 급정지 감지. 정지해 있어도 z축에 중력 약 9.8m/s²가 나온다(2일차에 관찰한 값).
- **카메라 영상**
  - `rgb8`/`bgr8`은 uint8 (H, W, 3), `32FC1`은 float32 깊이(m), `16UC1`은 uint16 깊이(mm)다. OpenCV는 BGR 순서다.
  - `cv_bridge`는 7일차 YOLO 가상환경의 numpy 버전과 충돌하기 쉬워서 직접 변환 함수(`image_utils.py`)를 만든다.
  - `msg.step`(한 줄의 바이트 수)이 `width × 채널 수`보다 클 수 있으니 그대로 reshape하면 안 된다.

## 문제와 해결
| 문제 | 원인 | 해결 |
|---|---|---|
| Docker의 n8n에서 `localhost:8000/chat` 호출이 실패할 수 있음 | 컨테이너 안의 `localhost`는 컨테이너 자신이다. | `http://host.docker.internal:8000`으로 부르기로 정리했다. 4-3 실습에서 바로 쓴다. |
| 문의가 여러 건 몰리면 무료 LLM 한도에 걸릴 수 있음 | n8n은 아이템마다 HTTP Request를 바로 실행한다. | Loop Over Items로 1건씩 보내고 Wait 5초를 넣는다. 2주차 429 문제와 같은 원리다. |
| 깊이 영상을 numpy로 바꿀 때 모양이 틀어질 수 있음 | 한 줄의 실제 바이트 수(`step`)가 `width × 채널`보다 클 수 있다. | 변환 함수에서 `step` 기준으로 자른 뒤 reshape하기로 했다. ②에서 `image_utils.py`에 넣는다. |
| SW 안전 노드만 믿으면 안 됨 | 현장의 기능 안전은 인증된 하드웨어가 맡는다. | `safety_stop`은 감속을 맡는 보조 기능으로 이해했다. 10일차에 Nav2 `collision_monitor`와 직렬로 연결한다. |
