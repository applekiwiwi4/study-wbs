## AI Agent — 3-2 LangGraph 실습 (CS 에이전트 만들기)
**배운 개념 (내 말로)**
- **정확한 조회는 코드가 하고, LLM에게는 결과만 알려 준다.**
  - `find_order_id`: 정규식 `HB-\d{8}-\d{3}`으로 주문번호를 찾는다. LLM이 필요 없다.
  - `lookup_order`: `orders.csv`에서 주문 상태, 운송장, 배송완료일을 찾는다. 실제 회사라면 주문 DB나 사내 API를 부르는 자리다.
  - `@tool`을 붙이면 같은 함수를 LLM이 쓸 수 있는 도구(`order_status`)로 만들 수 있다. 도구 설명(독스트링)이 LLM이 도구를 고르는 기준이 된다.
- **`create_agent`로 ReAct 에이전트를 먼저 만들어 봤다.**
  - 도구는 `order_status`와 `search_docs`를 줬다. LLM이 스스로 도구를 골라 부르고, 결과를 보고 답했다.
  - 체크포인터를 붙여서 "그럼 카드 취소는 언제 반영돼요?"라는 이어지는 질문도 앞 대화의 주문을 기억했다.
- **직접 설계한 CS 에이전트 (`agent.py`)**
  - 흐름: `classify → (order) → retrieve → draft → review`
  - `classify`: 2-1 구조화 출력 분류기를 쓴다. LLM이 주문번호를 놓치면 `find_order_id`로 한 번 더 찾는다.
  - `after_classify`: 주문번호가 있는 배송·환불 문의만 `order`로 보낸다. 나머지는 바로 `retrieve`로 간다.
  - `retrieve`: 2-3 RAG `search()`를 쓴다. `DOC_TYPES` 표로 문의 종류에 맞는 문서에서만 찾는다(고장AS는 manual과 policy, 배송은 policy와 faq).
  - `draft`: 1-6 `REPLY_RULES`에 분류 결과, 주문 조회 결과, 근거 문서를 붙인다. 최근 대화 6개와 함께 LLM에 넘긴다.
  - `review`: 긴급도가 높거나 `needs_human`이면 위험 문의로 본다.
    - 승인 모드(`HUMAN_REVIEW=on`)면 `interrupt`로 멈춘다.
    - 승인 모드가 아니면 답 앞에 `[상담원 확인 필요]`를 붙인다.
- **State가 상담 티켓이다.** 칸은 `messages`(add_messages로 이어 붙임), `ticket`, `order_info`, `context`, `sources`, `answer`다.
- **`handle()`과 `resume()`으로 감쌌다.**
  - `handle(question, thread_id)`: 문의 한 건을 처리한다. 결과는 `done`이거나, 승인을 기다리는 `waiting_review`다.
  - `resume(thread_id, "approve" | "edit", text)`: 상담원의 결정으로 이어서 실행한다.

**내가 만든 것**
- `src/csagent/tools.py`: `find_order_id`, `lookup_order`, `order_status`
- `scripts/08_tool_agent.py`: `create_agent` 맛보기
- `src/csagent/agent.py`: State, 노드 5개, 조건 엣지, `build_graph`, `handle`, `resume`

**결과 (경로 점검)**
| 문의 | 지나간 노드 |
|---|---|
| 배송 지연 + 주문번호 | classify → order → retrieve → draft → review |
| 공기청정기 E3 | classify → retrieve → draft → review |
| 제습기 연기 | classify → retrieve → draft → review에서 `[상담원 확인 필요]`, 승인 모드면 멈춤 |
| 단순 변심 반품 | classify → retrieve → draft → review |

- 지금까지 만든 세 가지 방법을 비교했다.
  - 1일차 답변 초안 체인: 주문 상태도 규정도 모른다.
  - 2일차 RAG `ask()`: 규정 근거는 있지만 주문 상태는 모른다.
  - CS 에이전트: 주문 조회 결과와 규정 근거를 함께 써서 답한다.
- 승인 모드에서 위험 문의는 `waiting_review`로 멈췄다. `resume(..., "edit", 수정본)`을 하면 상담원이 고친 답이 최종 답이 됐다. "필터 교체 주기?" 같은 일반 문의는 멈추지 않았다.

## ROS — 자율주행 과정 3일차 ① 이론 (Topic·Service와 로봇 뼈대)
**배운 개념 (내 말로)**
- **ROS 2는 운영체제가 아니라 미들웨어다.** 로봇 SW를 노드로 나누고 서로 통신하게 해 준다.
  - ROS 1과 달리 중앙 마스터가 없다. DDS가 서로를 자동으로 찾기 때문에 마스터 하나가 죽어서 전체가 멈추는 일이 없다.
- **통신 방식 고르는 기준**
  - Topic: 계속 흐르는 데이터 (`/scan`, `/odom`, `/cmd_vel_raw`)
  - Service: 바로 끝나는 질의와 설정 (`/robot_status`, 지도 저장)
  - Action: 오래 걸리고 취소가 필요한 작업 (`navigate_to_pose`)
  - Parameter: 튜닝값 (감속·정지 거리, 순찰 속도)
- **QoS는 "어떻게 전달할지"의 약속이다.**
  - Reliability: `RELIABLE`은 재전송을 보장해서 명령과 상태에 쓴다. `BEST_EFFORT`는 최신 값을 우선하고 유실을 허용해서 센서에 쓴다.
  - Durability: `TRANSIENT_LOCAL`이면 늦게 구독한 노드도 마지막 값을 받는다. `/map`이나 고정 TF에 쓴다.
  - History: `KEEP_LAST(10)`처럼 최근 n개만 보관한다.
  - 발행자와 구독자의 QoS가 안 맞으면 메시지가 오지 않는다. 오류도 안 나서 찾기 어렵다. 센서 구독에는 `qos_profile_sensor_data`를 쓴다.
- **`colcon build --symlink-install`**: .py 파일을 복사하지 않고 링크로 연결한다.
  - 기존 파일을 고치면 다시 빌드하지 않아도 반영된다.
  - 새 파일, 새 실행 이름, 새 launch를 추가했을 때만 다시 빌드한다.
- **이중 안전 배선 (오늘의 핵심)**
  - 순찰 노드는 바퀴에 직접 명령하지 못하고 `/cmd_vel_raw`로만 보낸다.
  - 안전 노드(`safety_stop`)만 `/cmd_vel`로 바퀴에 명령한다.
  - 병렬 구조(안전 노드가 옆에서 감시만 함)에서는 안전 노드가 죽으면 로봇이 계속 달린다.
  - 직렬 구조(최종단)에서는 안전 노드가 죽으면 로봇이 멈춘다. 고장 나면 안전한 쪽으로 멈추는 것(Fail-safe)이다.
- **rclpy 노드 골격**: 노드 안에서 `create_publisher`, `create_subscription`, `create_timer`를 만든다. 실행은 `rclpy.init()` → 노드 생성 → `rclpy.spin()` → `destroy_node()` → `try_shutdown()` 순서다.

## 문제와 해결
| 문제 | 원인 | 해결 |
|---|---|---|
| LLM 분류기가 주문번호를 빠뜨릴 수 있음 | 구조화 출력이라도 LLM이 긴 문장에서 형식이 정해진 값을 놓칠 때가 있다. | `classify` 노드에서 `order_id`가 비어 있으면 정규식 `find_order_id`로 대화 전체를 한 번 더 찾게 했다. 정확한 형식의 값은 코드가 더 믿을 만하다. |
| 이어지는 질문("그거 언제 와요?")만으로는 분류가 안 됨 | 마지막 질문 한 줄에는 제품이나 주문 정보가 없다. | 대화가 2개 이상이면 `history()`로 최근 6개 대화를 묶어서 분류하게 했다. |
| 고장 문의인데 배송 정책 문서가 검색될 수 있음 | 모든 문서에서 비슷한 조각을 찾으면 다른 종류 문서가 섞인다. | `DOC_TYPES` 표로 문의 종류별로 찾을 문서 종류를 제한했다. |
| 안전 노드가 죽으면 로봇이 계속 달릴 수 있음 | 안전 노드가 명령을 옆에서 감시만 하는 병렬 구조였다. | 모든 주행 명령이 안전 노드를 거치는 직렬 구조(`/cmd_vel_raw` → `safety_stop` → `/cmd_vel`)로 이해했다. |

## English (30 min) — Naps
- 영상: [Talking about naps](https://www.bbc.co.uk/learningenglish/english/features/real-easy-english/251114)
- 새 단어
  - take a nap (낮잠 자다), I'm exhausted. (완전 지쳤어.)
  - doze off (깜빡 졸다), feel refreshed (개운하다), stay up late (늦게까지 깨어 있다)
- 추가로 정리한 단어
  - snooze (잠깐 졸다, 선잠. 알람의 '다시 알림' 버튼도 snooze), yawn (하품하다, 하품)
  - crash (곯아떨어지다. 편하게 말할 때), afterwards (그 후에, 나중에)
  - avoid (피하다), worse (더 나쁜. bad의 비교급)
  - actual process (실제 과정), as bad as ~ (~만큼 나쁜)
  - moment (순간, 잠깐. at the moment는 "지금")
- 대화: *I stayed up late, and I dozed off in class! — Take a quick nap. You'll feel refreshed.*
- 말하기·쓰기 (낮잠 3문장)
  1. Sometimes, I take a short nap after lunch.
  2. I stayed up late last night, so I dozed off in class.
     - 문장 두 개는 쉼표만으로 잇지 않고 `so`로 잇는다. 어제 일이라 과거형 `dozed`다.
  3. After a 20-minute nap, I feel refreshed.
     - 시간 길이는 `during`이 아니라 `for`다(`for 20 minutes`). 명사를 꾸밀 때는 `a 20-minute nap`처럼 하이픈과 단수.
