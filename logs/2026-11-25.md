## AI Agent — 4-4 Dify 노코드 AI 앱 이론
**배운 개념 (내 말로)**
- **Dify는 AI 챗봇과 AI 앱을 화면에서 조립하고, 버튼 하나로 웹이나 API로 공개하는 도구다.** 기획자나 현업 담당자도 만들 수 있다. 고객 FAQ 챗봇, 사내 규정 Q&A 봇, 개발 전 프로토타입에 쓴다.
- **세 도구의 역할 나누기**
  - LangGraph(코드): 복잡한 AI 판단 흐름. 우리 프로젝트의 CS 에이전트 두뇌
  - n8n: 시스템 연결과 자동 실행. 문의 접수와 긴급 알림
  - Dify: 사람이 대화하는 앱과 화면. 고객용 공개 챗봇
- **지식베이스 = 화면으로 하는 RAG.** 2일차 단계와 하나씩 짝지어진다.
  - 읽기 → 파일 업로드
  - 자르기 → 청크 설정(구분자, 최대 길이, 겹침)
  - 임베딩 → 인덱스 방식. "고품질"은 임베딩으로 뜻을 찾고, "경제적"은 키워드만 색인한다.
  - 검색 → 벡터 / 전문(키워드) / 하이브리드, Top K, 점수 기준
  - 평가 → 검색 테스트 화면
  - 부모-자식 분할: 작은 조각으로 정확히 찾고, 답변에는 그 조각이 속한 큰 단락을 넣어 맥락을 보충한다.
- **앱 종류**: 챗봇, 에이전트(3일차 `create_agent`와 비슷), 텍스트 생성, **Chatflow**(대화 + 분기 흐름도), Workflow(대화 없는 일괄 처리)
- **Chatflow 노드 ↔ CS 에이전트**
  - 질문 분류기 ↔ `classify` 노드와 조건 엣지
  - 지식 검색 ↔ `retrieve`
  - LLM ↔ `draft`
  - HTTP 요청 ↔ `order` (주문 조회 API)
  - 매개변수 추출 ↔ 구조화 출력 (문장에서 주문번호 뽑기)
  - LLM 노드의 메모리 ↔ 체크포인터
- **변수**: 앞 노드 결과는 `{{#노드.변수#}}`로 쓴다. 시스템 변수는 `sys.query`(질문), `sys.conversation_id`(대화방 번호)다.
- **공개와 운영**: 웹앱 주소(포트폴리오 데모 링크), 웹사이트 채팅 버튼, API, DSL(YAML) 내보내기. 로그로 틀린 답을 찾고, 좋은 답은 주석(Annotation)으로 등록해 같은 질문에 그대로 쓴다.
- **Dify Cloud에서 내 PC의 API는 안 보인다.** Cloud 서버 입장에서 localhost는 자기 자신이다. `cloudflared tunnel --url http://localhost:8000`으로 임시 주소를 만들고, 실습이 끝나면 반드시 끈다.
- **Sandbox 무료 플랜**: 메시지 크레딧 200개, 앱 5개, 문서 50개, 50MB. 크레딧은 금방 떨어지므로 모델 공급자에 내 Gemini 무료 키를 등록해서 쓴다.

**확인 문제 (내 답)**
1. 고품질 인덱스는 임베딩으로 뜻을 찾고, 경제적 인덱스는 키워드 색인만 해서 비용이 없지만 의미 검색이 안 된다.
2. 질문 분류기(Question Classifier)
3. Dify Cloud에서 localhost는 Dify 서버 자신이다. cloudflared 터널로 임시 공개 주소를 만들거나 API를 배포한다.
4. 모델 공급자에 내 Gemini나 Groq 키를 등록한다.

## ROS — 자율주행 과정 6일차 ① 이론·실습 준비 (SLAM 운영 맵과 검수, M2)
**배운 개념 (내 말로)**
- **SLAM은 "지도가 있어야 위치를 알고, 위치를 알아야 지도를 만든다"를 동시에 푼다.** slam_toolbox 구조:
  - Front-end(스캔 매칭): 새 스캔을 직전 스캔·지도와 맞춰 이동량을 추정한다.
  - Pose Graph: 0.5m나 0.5rad 움직일 때마다 자세를 노드로 저장하고, 상대 이동을 간선으로 잇는다.
  - 루프 클로저: 왔던 곳에 다시 오면 알아보고 간선을 더한다.
  - Back-end(최적화): 모든 간선이 가장 잘 맞도록 자세 전체를 다시 계산해 쌓인 오차를 나눠 줄인다.
  - **지도를 그릴 때 반드시 한 바퀴 돌아 출발점으로 돌아온다.** 그래야 루프 클로저가 전체 경로를 바로잡는다.
- **점유 격자 지도** = `.pgm`(흰색 빈 공간, 검은색 장애물, 회색 모름) + `.yaml`
  - 핵심 값은 `resolution`(1픽셀 = 5cm)과 `origin`(이미지 왼쪽 아래 픽셀의 map 좌표)이다.
  - 실제 좌표 = origin + 픽셀 좌표 × resolution. 그래서 이미지 편집기에서 그림 크기를 바꾸면 좌표가 모두 틀어진다.
- **표준 좌표계 (REP-105)**: `map` → `odom` → `base_link` → 센서 프레임
  - `map`: 장기적으로 정확하지만 보정 순간에 값이 튈 수 있다.
  - `odom`: 부드럽고 연속적이지만 오차가 쌓인다.
  - SLAM과 AMCL은 `map→base_link`가 아니라 `map→odom`을 발행한다. TF 트리에서 한 프레임의 부모는 하나여야 하는데, `odom→base_footprint`는 이미 오도메트리가 맡고 있기 때문이다. SLAM은 "odom이 얼마나 틀렸는지"만 보정한다.
  - 방향 규칙(REP-103): x 앞, y 왼쪽, z 위, 반시계가 +. 카메라 광학 좌표계만 예외(z 앞, x 오른쪽, y 아래)다.
- **월드 ≠ 맵**
  - 월드(.sdf)는 사람이 지은 3D 공간이다. 벽, 랙, 바닥 표식, 작업자가 들어간다.
  - 맵(.pgm)은 로봇이 LiDAR로 본 면만 담는다. 높이가 없는 바닥 표식은 안 보인다.
  - 시뮬레이션에서는 둘 다 있으니 "로봇이 그린 맵이 실제와 얼마나 같은가"를 숫자로 검수할 수 있다. 이것이 맵 검수(Map QC)다.
- **Project LIFT 좌표 규약**: 1층은 12m × 9m, 2층은 1층을 y로 +11m 옮긴 위치, 랙 3열 사이 통로 폭 1m. Gazebo 월드 좌표 = Nav2 map 좌표로 맞춘다. Gazebo에는 층 개념이 없어서 두 층을 한 월드에 나란히 둔다.
- **SLAM 지도 원점 맞추기**: 오도메트리는 스폰한 자리를 (0, 0)으로 시작한다. 그래서 S1에서 스폰해 만든 지도는 월드 좌표와 스폰 좌표만큼 어긋난다. SLAM 지도 origin + 스폰 좌표 = 월드 기준 origin이다. 스폰할 때 yaw가 0이어야 이 덧셈이 맞다.

**실습 준비 확인**
```bash
cd ~/project_lift && git log --oneline | head -3     # 5일차 커밋
which gimp eog                                         # 지도 후처리·보기 도구
ls ~/.gz/fuel/fuel.gazebosim.org/openrobotics/models/  # standing person 모델
ros2 node list; pgrep -f "gz sim"                      # 둘 다 비어 있어야 함
```
- 오늘 실습에서 주의할 점을 미리 적어 두었다: SLAM과 지도 서버를 동시에 켜면 `/map`을 두 노드가 발행해서 로봇이 위치를 잃는다. SLAM을 끈 뒤에 지도 서버를 켠다.

## 문제와 해결
| 문제 | 원인 | 해결 |
|---|---|---|
| Dify Cloud에서 우리 주문 조회 API를 부를 수 없음 | Cloud 서버 입장에서 `localhost:8000`은 Dify 서버 자신이다. | cloudflared 임시 터널로 https 주소를 만들어 쓰기로 했다. 실습 후 터널을 꼭 끈다. |
| Sandbox 메시지 크레딧 200개가 금방 떨어질 수 있음 | 기본 모델은 Dify 크레딧을 쓴다. | 모델 공급자에 내 Gemini 무료 키를 등록하기로 했다. |
| SLAM 지도의 좌표가 월드 좌표와 어긋남 | 오도메트리와 SLAM 지도가 스폰 자리를 (0, 0)으로 잡는다. | SLAM 지도 origin에 스폰 좌표를 더해 월드 기준으로 바꾼다. yaw 0으로 스폰해야 한다. ②에서 `align_map.py`로 한다. |
| 지도 이미지 크기를 바꾸면 위치가 틀어질 수 있음 | 좌표는 origin과 resolution으로 계산되기 때문이다. | 후처리할 때는 픽셀 크기를 바꾸지 않고 칠하기만 하기로 했다. |
